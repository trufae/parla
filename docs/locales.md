# Localization (i18n/l10n)

Parla uses the standard GNU gettext stack that is already shipped with GLib,
GTK and libadwaita. The build system is Meson and the translation domain is
`parla`.

The UI is translated to **Catalan** (`ca`); Dutch (`nl`) is also shipped.
Coverage grows by wrapping more strings with `_()` and adding the source file
to `po/POTFILES`; no architecture change is needed for that.

## How it works

* Translatable strings in the Vala sources are wrapped with `_("...")`.
* `src/main.vala` initializes gettext before the first widget is built:
  `setlocale()`, `bindtextdomain()`, `bind_textdomain_codeset()` and
  `textdomain()`.
* `meson.build` defines the C macro `GETTEXT_PACKAGE="parla"` so the
  `_()`/`C_()`/`N_()` macros generated by `valac` can resolve the domain.
* `po/meson.build` imports the Meson `i18n` module with the `glib` preset,
  which runs `xgettext` with the right keyword and flag set.
* `po/POTFILES` lists the source files that contain translatable strings.
* `po/LINGUAS` lists the languages that are shipped.
* `po/parla.pot` is the translation template; `po/ca.po` is the Catalan
  catalog; compiled `ca/LC_MESSAGES/parla.mo` files are installed under
  `<prefix>/share/locale`.

## Selecting a language on startup

Settings → General → Language offers **System Language** (the default),
**English**, and all catalogs listed in `po/LINGUAS`. The current translations
appear as **Català** and **Nederlands**, using their own names. Selecting a
different language opens a **Restart** / **Cancel** dialog: Restart saves the
choice and relaunches Parla, while Cancel keeps the previous selection.
Existing widgets do not support live retranslation.

The choice is stored as a locale code in `[General] language` in `settings.ini`;
an empty or unsupported code follows the system. The list of codes is generated
from `po/LINGUAS` at build time. Add an autonym in `src/localization.vala` for
new languages; otherwise their code is displayed.

On macOS, Finder launches without locale environment variables use the native
preferred-language list. An explicit choice also works when the process starts
in the C locale, without changing date or number formatting.

With **System Language** selected, gettext follows the usual GNU locale
environment variables. The simplest way
to force a language for one launch is to set `LC_ALL` to a UTF-8 locale that
is installed on the system:

```sh
# Run Parla in Catalan
LC_ALL=ca_ES.UTF-8 parla

# Run Parla in Catalan from a local build/install tree
LC_ALL=ca_ES.UTF-8 ./builddir/parla
```

If the locale is **not installed** in the system C library, `LC_ALL` will
produce a warning and fall back to the C locale. In that case use `LANG` plus
the `LANGUAGE` override, which does not require the locale to be present:

```sh
# LANGUAGE overrides the message language without touching libc locale data
LANG=en_US.UTF-8 LANGUAGE=ca parla
```

`LANGUAGE` accepts a colon-separated preference list, so testing a fallback
chain is also possible:

```sh
LANGUAGE=ca:es:en parla
```

### Useful variables

| Variable | Effect |
|----------|--------|
| `LANG` | Default language and format locale. |
| `LC_ALL` | Overrides all other `LC_*` variables and `LANG`. |
| `LANGUAGE` | GNU gettext message language; overrides `LC_ALL` for translations. |
| `LC_MESSAGES` | Only the message catalog language. |

For day-to-day use, desktop users normally set `LANG` or `LC_ALL` in their
session and Parla will follow it automatically.

## For translators

### File layout

```
po/
├── LINGUAS          # one language code per line
├── POTFILES         # source files scanned by xgettext
├── meson.build      # i18n.gettext(...) with the glib preset
├── parla.pot        # generated template (do not edit by hand)
├── ca.po            # Catalan catalog
└── nl.po            # Dutch catalog
```

`po/ca.po` is an ordinary PO file: edit it in place with any PO editor. After
`parla-update-po` marks entries as fuzzy, review them rather than accepting the
suggestion blindly, since gettext matches on similar English text and the
existing translation often belongs to a different string.

Check a catalog before committing:

```sh
msgfmt -c --statistics po/ca.po -o /dev/null
```

A clean run reports no untranslated and no fuzzy messages.

### Add a new language

1. Add the language code to `po/LINGUAS`, for example `de` for German.
2. From the build directory run the update target:

   ```sh
   meson compile -C builddir parla-update-po
   ```

   Meson creates `po/de.po` from `po/parla.pot`.
3. Translate the strings in `po/de.po`. Any PO editor (Poedit, Gtranslator,
   Weblate, etc.) can open the file.
4. Rebuild so the new `.mo` file is generated and installed:

   ```sh
   meson compile -C builddir
   ```

### Update catalogs after code changes

When developers add, remove or change `_()` strings in the Vala sources, the
catalogs must be refreshed:

```sh
# Regenerate po/parla.pot from the current sources
meson compile -C builddir parla-pot

# Merge the new strings into every po/*.po file
meson compile -C builddir parla-update-po
```

`parla-update-po` rewrites `po/parla.pot` as well, so running only the second
command is enough in most cases. It preserves the existing `msgstr` values,
marks near-matches as `#, fuzzy` and appends genuinely new entries as empty.

Translators should then fill in the new or fuzzy entries. Entries that are no
longer in the sources end up commented out at the bottom of the file; delete
them when editing by hand.

### Adding a source file to POTFILES

A Vala file only becomes translatable once it is listed in `po/POTFILES`. Keep
the list alphabetical:

```sh
echo 'src/new_dialog.vala' >> po/POTFILES
sort -o po/POTFILES po/POTFILES
meson compile -C builddir parla-update-po
```

### Marking strings in Vala

Use the GLib gettext helpers:

```vala
// Simple label
label.label = _("Select a chat");

// String with context (same English word, different meaning)
row.title = C_("Connection state", "Not connected");

// Plural forms (never build plurals by appending "s")
status_label.label = ngettext ("%u chat", "%u chats", n).printf (n);

// Delayed translation: const arrays hold N_(), translate at the point of use
const string[] hints = { N_("Add a profile"), N_("Set up account") };
label.label = _(hints[0]);
```

Translator comments can be added with the `/// TRANSLATORS:` convention so
xgettext copies them into the `.pot` file.

### What is translated today

All files listed in `po/POTFILES` are translated; run

```sh
cat po/POTFILES
```

for the current list. It covers the chat, settings and account setup surfaces:

* Command-line options (`src/application.vala`) and the main window, including
  its app menu and keyboard shortcut menu (`src/window.vala`).
* Chat list, message rows, composer and the media bar
  (`src/chat_row.vala`, `src/message_row.vala`, `src/compose_bar.vala`,
  `src/conversation_media_bar.vala`, `src/conversation_view.vala`,
  `src/message_actions.vala`, `src/full_message_dialog.vala`).
* Shared destructive-action confirmations, used by the message, chat and group
  flows (`src/models.vala`).
* Dialogs: chat info, new group/channel, contact picker, search results, image
  viewer, sticker picker and the in-chat app manager
  (`src/chat_info_dialog.vala`, `src/new_group_dialog.vala`,
  `src/contact_picker_dialog.vala`, `src/search_results_view.vala`,
  `src/image_viewer.vala`, `src/sticker_picker.vala`,
  `src/webxdc_manager_dialog.vala`).
* The settings dialog (`src/settings_dialog.vala`), including the Chatmail Core
  updater, proxy configuration and link-tracking filter list.
* Voice message playback, transcription and recording errors, including the
  native macOS microphone permission flow.
* Profile editing and storage details, invite codes, second-device setup,
  account creation, classic email login and relay management.
* The gallery, pinned-message and sticker managers, message details, quick
  chat switcher, Webxdc bar and built-in error dialogs, and both tray menus.

Protocol identifiers, file formats, log messages and content supplied by the
core or by Webxdc apps are not UI translations. Keep identifiers such as
`"Audio"`, `"Group"` and `"Configured"` unchanged in RPC calls, comparisons
and settings files. Translate display labels separately. Constant labels use
`N_()` and are translated with `_()` when they are displayed; the profile
creation menu keeps its untranslated identifiers for action dispatch.

The Catalan catalog uses informal singular address, imperative action labels,
`xat`, `adhesiu`, `adjunció`, `desar` and `suprimir` consistently.

### Plurals and composed strings

Catalan, like most languages, needs plural forms, so avoid English `+ "s"`
pluralisation. Use `ngettext()` for a plain count:

```vala
label = ngettext ("%u chat", "%u chats", n).printf (n);
```

When a plural noun is embedded in a longer sentence, format it with
`ngettext()` and pass it as a parameter to the enclosing translated string,
as the storage rows in `src/profile_dialog.vala` do. Use complete translated
sentences for gallery save actions so grammatical gender can vary by item type.

Long sentences that are built by concatenating string literals should be joined
*inside* the `_()` call, not outside it, otherwise translators get a fragment
they cannot reorder:

```vala
// Wrong: the parts cannot be reordered in the target language
var body = _("First half of the sentence.") + _("Second half.");

// Right: one translatable unit
var body = _("First half of the sentence. Second half.");
```

The same applies to sentence fragments that are concatenated depending on
context (for example the group/channel variants): use `_("Full text for a "
+ "group")` and `_("Full text for a channel")` rather than a translated prefix
plus an untranslated suffix.

When a sentence is built from a translated prefix and a value, keep the
punctuation and spacing next to the placeholder so the format string is
self-contained: `_("Remove failed: %s").printf (reason)`.

### Desktop and AppData files

The desktop entry contains Catalan `GenericName`, `Comment` and `Keywords`
fields. The AppStream file contains Catalan summaries, descriptions and
screenshot captions using `xml:lang="ca"`. These metadata translations live
in `data/io.github.trufae.Parla.desktop` and
`data/io.github.trufae.Parla.appdata.xml`; edit them alongside the catalog.
The desktop strings are also extracted into gettext, including the summary
shared with the About dialog.

## Testing a translation without installing

Parla first looks for catalogs beside its executable, under
`../share/locale`. macOS app bundles use `../Resources/share/locale` instead.
If neither contains a matching catalog, it uses the compiled `LOCALEDIR`. This keeps
translations working when Windows distributions or AppImages are relocated.
The macOS bundler compiles all catalogs listed in `po/LINGUAS` into the bundle.

To test the app's translations without installing it system-wide:

```sh
meson compile -C builddir
mkdir -p /tmp/parla-locale/bin /tmp/parla-locale/share/locale/ca/LC_MESSAGES
cp builddir/parla /tmp/parla-locale/bin/parla
msgfmt -c po/ca.po -o /tmp/parla-locale/share/locale/ca/LC_MESSAGES/parla.mo
LANG=en_US.UTF-8 LANGUAGE=ca /tmp/parla-locale/bin/parla --help
```

If `ca_ES.UTF-8` is installed, you can also use
`LC_ALL=ca_ES.UTF-8 /tmp/parla-locale/bin/parla`.
